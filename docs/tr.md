# Техническое решение проекта «MiniFeed»

## Введение
- **Краткое описание:**
 
  «MiniFeed» — учебный проект, в котором мы делаем прототип распределённой системы для публикации контента. Пользователи создают короткие текстовые посты, смотрят общую ленту, ставят и убирают лайки, пишут комментарии и видят количество просмотров постов.
Система разделена на несколько компонентов. Посты и комментарии хранятся на нескольких узлах хранения с копиями (репликами), а лайки и просмотры обрабатываются отдельным сервисом статистики через брокер сообщений. На этом примере мы показываем типичные проблемы распределённых систем: отказ одного узла, потерю и повторную доставку сообщений, разный порядок прихода событий и временную рассогласованность данных. 
- **Цель проекта:**  
  реализовать прототип распределённой платформы публикации контента, которая хранит посты на нескольких узлах, продолжает работать при отказе одного узла и корректно считает лайки и просмотры при повторной доставке и перестановке событий.
- **Задачи:**  
  •закрепить теорию по распределённым системам на практике;
  
  •разделить систему на несколько независимых компонентов;
  
  •распределить посты по узлам хранения и сделать их копии для отказоустойчивости;
  
  •передавать события лайков и просмотров асинхронно через брокер сообщений;
  
  •обработать ненадёжную и повторную доставку событий (at-least-once, идемпотентность, дедупликация);
  
  •обработать частичные отказы: недоступность узла хранения или сервиса статистики;
  
  •обработать разный порядок прихода событий (например, «снять лайк» пришло раньше «поставить лайк»);
  
  •использовать eventual consistency для данных, которым не нужна мгновенная согласованность (счётчики, копии постов).

## Глоссарий

| Термин | Определение |
|---|---|
| Пользователь | Участник системы, который создаёт и просматривает посты, пишет комментарии и ставит лайки. Определяется по имени, пароли в проекте не используются. |
| Пост | Созданная пользователем единица контента с текстом. После создания не изменяется. |
| Лента | Общий список постов от новых к старым. |
| Комментарий | Текстовое сообщение пользователя под определённым постом. После создания не изменяется. |
| Лайк | Положительная реакция пользователя на пост. Один пользователь может поставить на один пост не более одного лайка. |
| Просмотр | Факт открытия поста пользователем, который учитывается в статистике. |
| Статистика | Количество лайков и просмотров поста. |
| Событие | Сообщение о том, что в системе что-то произошло (например, пост просмотрели). Передаётся другому компоненту для асинхронной обработки. |
| API Gateway | Точка входа для всех запросов клиента. |
| Feed Service | Основной сервис: посты, комментарии, лента, размещение данных по узлам и репликация. |
| Stats Service | Сервис статистики: получает события, считает лайки и просмотры. |
| Узел хранения | Отдельный сервис со своей базой данных, который хранит посты и комментарии. |
| Основной узел | Узел, на который пост записывается и с которого читается в первую очередь. |
| Реплика | Копия поста и его комментариев на втором узле, нужна для отказоустойчивости. |
| Failover | Автоматическое переключение на реплику, если основной узел недоступен. |
| Read repair | Восстановление недостающей копии данных на узле, которое выполняется при чтении. |
| Message Broker | Брокер сообщений, который передаёт события между сервисами асинхронно. |
| At-least-once | Семантика доставки: сообщение доставляется как минимум один раз, возможны повторы. |
| Retry | Повторная попытка выполнить операцию или отправить сообщение после неудачи. |
| Идемпотентность | Свойство операции: повторное выполнение с теми же параметрами не меняет результат. |
| Дедупликация | Отбрасывание повторно пришедшего события по его уникальному идентификатору. |
| Частичный отказ | Ситуация, когда один компонент недоступен, а остальные продолжают работать. |
| Деградация | Работа системы с урезанной функциональностью при отказе компонента (например, лента без счётчиков). |
| Timeout | Время ожидания ответа, после которого запрос считается неуспешным. |
| Health check | Проверка доступности компонента запросом `GET /health`. |
| Eventual consistency | Модель согласованности: данные в разных местах могут временно отличаться, но без новых изменений со временем становятся одинаковыми. |
| Метка времени события | Время создания события, по которому Stats Service определяет, какое из двух событий (лайк или снятие лайка) новее. |

## Функциональные требования
Система должна предоставлять следующие функции:

1.Создание поста пользователем

2.Просмотр общей ленты постов

3.Просмотр отдельного поста

4.Добавление лайка к посту

5.Удаление ранее поставленного лайка

6.Добавление комментария к посту

7.Просмотр комментариев к посту

8.Просмотр количества лайков поста

9.Учёт просмотра поста

10.Просмотр количества просмотров поста

## Ограничения на предметную область

1.Посты и комментарии содержат только текст: пост до 500 символов, комментарий до 300 символов. Картинки, видео и файлы не поддерживаются.

2.Авторизация упрощённая: пользователь определяется по имени в заголовке X-User-Name, регистрация и пароли не реализуются.

3.Один пользователь может поставить на один пост не более одного лайка. Пользователь может убрать свой лайк.

4.Посты и комментарии нельзя редактировать и удалять.

5.Комментарии плоские (без ответов на комментарии).

6.Используется одна общая лента. Персональные рекомендации, подписки, личные сообщения, поиск и теги не реализуются.

7.Число узлов хранения фиксировано (три), добавление и удаление узлов во время работы не поддерживается.

8.Счётчики лайков и просмотров не обязаны обновляться мгновенно: допускается небольшая задержка.

9.Проект предназначен для демонстрации принципов распределённых систем и не является полноценной соцсетью.

## Нефункциональные требования
•**Разделение компонентов:** система состоит из нескольких взаимодействующих компонентов: работа с контентом (Feed Service и узлы хранения) и обработка статистики (брокер и Stats Service).

•**Асинхронное взаимодействие:** лайки и просмотры передаются через брокер сообщений. Обработка события просмотра не должна блокировать получение самого поста.

•**Доставка событий:** Используется семантика at-least-once. Если нет подтверждения обработки, сообщение отправляется повторно (retry). События не теряются при временной недоступности брокера или Stats Service.

•**Идемпотентность и дедупликация:** у каждого события есть уникальный идентификатор eventId; повторная доставка события не должна приводить к повторному учёту.Установка и снятие лайка идемпотентны: повторный запрос не меняет состояние. Создание поста и комментария идемпотентно по идентификатору, который задаёт клиент.

•**Распределение данных:** посты распределяются по трём узлам хранения примерно поровну (отклонение между узлами не более 20% при 1000 постов). Каждый пост хранится на двух разных узлах.

•**Отказоустойчивость:** система продолжает создавать и читать посты, комментарии и ленту при отказе любого одного узла хранения. Недоступность компонента определяется по timeout (1 секунда) и health check (раз в 5 секунд).

•**Изоляция отказов:** недоступность Stats Service или брокера не мешает получить пост, ленту и комментарии: они возвращаются без счётчиков.

•**Согласованность:** для статистики и копий постов допускается eventual consistency. Сразу после действия счётчик может быть неточным, но после обработки накопленных событий значение становится актуальным. После возвращения упавшего узла и чтения данных недостающие копии восстанавливаются.

•**Порядок событий:** если события лайка и снятия лайка одного пользователя пришли в Stats Service в неправильном порядке, итоговое состояние лайка всё равно должно соответствовать последнему действию пользователя.

•**Восстановление обработки:** после временного отказа Stats Service необработанные события обрабатываются после его восстановления, а уже обработанные повторно не учитываются.

•**Время отклика (локальная среда, до 50 одновременных запросов):** чтение и создание поста не более 200 мс, сборка ленты из 20 постов не более 500 мс, постановка и снятие лайка не более 200 мс (счётчик обновляется асинхронно).

•**Масштабируемость:** Feed Service не хранит состояние, поэтому его можно запускать в нескольких экземплярах.

•**Тестируемость:** архитектура позволяет отдельно показать: отказ узла хранения, повторную доставку сообщений, недоступность Stats Service, задержку обновления статистики.

•**Развёртывание:** вся система запускается одной командой docker compose up.

## Пользовательские сценарии

### Сценарий: создание поста

1. Пользователь выбирает создание нового поста и вводит текст.
2. Клиентское приложение отправляет запрос на создание поста в систему.
3. Система сохраняет пост.
4. Пользователь получает подтверждение, а пост появляется в общей ленте.

### Сценарий: просмотр общей ленты

1. Пользователь открывает общую ленту.
2. Клиентское приложение запрашивает список постов.
3. Система возвращает последние посты от новых к старым вместе с количеством лайков и просмотров.
4. Пользователь видит ленту и при необходимости загружает следующую страницу.

### Сценарий: просмотр поста

1. Пользователь выбирает пост в ленте.
2. Клиентское приложение запрашивает пост.
3. Система возвращает содержимое поста и счётчики.
4. Факт просмотра формирует отдельное событие, которое передаётся на асинхронную обработку.
5. Сервис статистики обрабатывает событие и увеличивает счётчик просмотров.
6. Счётчик может обновиться с небольшой задержкой и не блокирует получение поста.

### Сценарий: добавление лайка

1. Пользователь открывает пост и нажимает «Нравится».
2. Клиентское приложение отправляет запрос на добавление лайка.
3. Система принимает запрос и передаёт событие на обработку.
4. Если лайка этого пользователя на этом посте ещё нет, он создаётся.
5. Если лайк уже существует, состояние системы не меняется.
6. Пользователь видит пост с лайком, счётчик обновляется с небольшой задержкой.

### Сценарий: удаление лайка

1. Пользователь открывает пост, которому ранее поставил лайк, и нажимает «Убрать лайк».
2. Клиентское приложение отправляет запрос на удаление лайка.
3. Система принимает запрос и передаёт событие на обработку.
4. Лайк пользователя снимается.
5. Счётчик лайков уменьшается с небольшой задержкой.
6. Повторное снятие лайка ничего не меняет.

### Сценарий: добавление комментария

1. Пользователь открывает пост и вводит текст комментария.
2. Клиентское приложение отправляет запрос на создание комментария.
3. Система сохраняет комментарий, связанный с постом и пользователем.
4. Пользователь получает подтверждение.
5. Комментарий становится виден в списке комментариев поста.

### Сценарий: просмотр комментариев

1. Пользователь открывает пост.
2. Клиентское приложение запрашивает комментарии к посту.
3. Система возвращает список комментариев от старых к новым.
4. Пользователь видит комментарии.

### Сценарий: временная недоступность сервиса статистики

1. Пользователь открывает пост.
2. Система возвращает содержимое поста без счётчиков, если сервис статистики недоступен.
3. Формируется событие просмотра, но Stats Service временно недоступен.
4. Недоступность Stats Service не мешает просмотру постов, ленты и комментариев.
5. Событие сохраняется и обрабатывается после восстановления сервиса.
6. После обработки накопленных событий счётчики приходят к актуальному значению.

### Сценарий: повторная доставка события просмотра

1. Пользователь открывает пост.
2. Система формирует событие просмотра с уникальным идентификатором.
3. Из-за повторной доставки одно и то же событие поступает в сервис статистики дважды.
4. Сервис статистики проверяет идентификатор события.
5. Первый экземпляр события обрабатывается.
6. Второй экземпляр определяется как дубликат и не обрабатывается повторно.
7. Просмотр учитывается один раз.

### Сценарий: отказ узла хранения

1. Один из узлов хранения становится недоступным.
2. Пользователь открывает ленту, посты и комментарии, а также создаёт новые посты и комментарии как обычно.
3. Система возвращает данные благодаря копиям на других узлах.
4. Допускается задержка не более 1 секунды на обнаружение недоступного узла.
5. После восстановления узла недостающие данные восстанавливаются при чтении.
